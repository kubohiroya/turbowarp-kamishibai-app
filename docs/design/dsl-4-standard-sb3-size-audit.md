# Standard SB3 のサイズ監査

関連は [Issue #1134](https://github.com/kubohiroya/turbowarp-kamishibai-app/issues/1134)、[PR #1133](https://github.com/kubohiroya/turbowarp-kamishibai-app/pull/1133)、[Issue #586](https://github.com/kubohiroya/turbowarp-kamishibai-app/issues/586)。

## 上限と実測

ブラウザー配布ビルドが検査するのは、ZIP 全体のサイズと別に、展開後の `project.json` のサイズである。16 MiB は16,777,216バイト。rc.84 と同じ入力・版情報で WASM 圧縮だけを選び、同じ SB3 ビルダーで比較した。

| SB3                             |    ZIP 全体 | 展開後の `project.json` | 16 MiB までの余裕 |
| ------------------------------- | ----------: | ----------------------: | ----------------: |
| rc.82                           | 8,326,722 B |            16,767,935 B |           9,281 B |
| rc.83                           | 8,332,572 B |            16,779,479 B |          −2,263 B |
| rc.84                           | 8,274,462 B |            16,698,403 B |          78,813 B |
| rc.84 と同じ入力で3本を圧縮     | 7,956,343 B |            15,353,023 B |       1,424,193 B |
| rc.84 と同じ入力で SIMD 2本のみ | 7,801,130 B |            15,135,495 B |       1,641,721 B |

rc.84 の `project.json` では拡張 URL が9,916,960バイト、拡張ストレージが6,778,182バイトを占める。拡張ストレージのうち6,777,225バイトが PoseNet のモデル記述子。ステージの SVG は4件で計3,278バイトあり、ZIP に各1件入っている。JSON 内では512バイト以上の同一文字列をパスをまたいで調べ、大きなペイロードの二重格納は見つからなかった。

## 実施した削減

Teachable Machine の同梱メンバーは4,022,532バイト。このうち、通常、SIMD、スレッド付き SIMD の WASM を表す3本の Base64 リテラルが計1,561,820バイトある。3本の SHA-256 はすべて異なり、バックエンドの選択に使う。

| WASM              | 元の Base64 | DEFLATE 後の Base64 |
| ----------------- | ----------: | ------------------: |
| 通常              |   414,832 B |            同梱なし |
| SIMD              |   566,128 B |           189,888 B |
| スレッド付き SIMD |   580,860 B |           194,908 B |

生成時に npm 配布物の各 WASM と埋め込み元をバイト単位で照合する。通常版は削除し、SIMD の2本を圧縮する。WASM バックエンドがファイルを参照した時に初めて復元し、元と同一の data URL をキャッシュする。SIMD を検出できない場合、WASM 初期化をバイナリの取得前に止める。明示的な WASM 指定は JavaScript CPU に切り替える。自動選択は WebGPU と WebGL を先に試し、どちらも使えない場合に CPU へ進む。

展開器を含むメンバーは2,850,351バイト。rc.84 から展開後の JSON が1,562,908バイト、ZIP 全体が473,332バイト減った。3本を圧縮した試作と比べると、通常版の削除で JSON がさらに217,528バイト減った。旧SB3が同じタブですでに読み込んだランタイムは共有の対象になる。新しいランタイムの選択条件を適用するには、Editor を再読み込みして新しいSB3を開く。

## 公式 TurboWarp Editor でのポーズ推論の性能比較

2026年11月5日に macOS の Apple M1 Max と Chrome 156.0.8078.80 で測定した。公式 Editor の VM に候補拡張を登録し、SB3 と同じ PoseNet の重み、公開ポーズ分類モデル `R9i0aRHth`、固定の320×240合成フレームを使った。単一スレッドの SIMD 版は TensorFlow.js のスレッド検出フラグだけを無効にした。WASM 2方式の比較と WebGPU を含む比較は別々に実施し、各方式を新規ブラウザコンテキストで3回測定した。各回15フレームのウォームアップ後に60フレームを測り、`estimatePose` と分類 `predict` の時間を合算した。カメラ取得、モデルの読込、画面描画は計測区間の外に置いた。

| 比較           | バックエンド           | WASM の実スレッド数 | フレーム数 |   中央値 |      p95 |
| -------------- | ---------------------- | ------------------: | ---------: | -------: | -------: |
| WASM 2方式     | WASM 単一スレッド SIMD |                   1 |        180 | 28.45 ms | 29.15 ms |
| WASM 2方式     | WASM スレッド付き SIMD |                   5 |        180 | 14.38 ms | 19.13 ms |
| WebGPU と WASM | WASM スレッド付き SIMD |                   5 |        180 | 13.48 ms | 17.79 ms |
| WebGPU と WASM | WebGPU                 |                   — |        180 | 12.05 ms | 14.35 ms |

同じ測定内で比較すると、スレッド付き SIMD は単一スレッド SIMD より中央値が約49%短く、この改善を根拠に同梱を維持する。WebGPU はスレッド付き SIMD より中央値が約11%、p95 が約19%短かった。いずれも指定したバックエンドで動作し、最上位の分類ラベルは一致した。

## 残る候補と互換性

| 対象                                      | 観測                                                                                                                                                                      | 次に必要な変更                                                                                                                                                                                                      |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PoseNet                                   | モデル定義と重み2本は別々で、現在の格納は1セット。各ファイルを DEFLATE して再度 Base64 化する試算では502,776バイト減り、復元結果も元のバイト列に一致した。                | 現在の Teachable Machine の記述子契約は Base64 のモデル実体を読む。別の符号化を導入する場合はバージョン付きの記述子と既存版の読み込み、旧ランタイムを持つSB3との組み合わせの検証が必要。                            |
| 拡張メンバー間の重複                      | 300文字超で本文が完全一致する関数は75群あり、内包する範囲を除いた重複分の上限は44,005バイト。同じ本文でも、メンバー固有の変数・クラス・インスタンスに依存する場合がある。 | 共通化するには、上流のモジュールエントリーと状態の所有者を確認し、生成時に共通モジュールを一度だけ束ねる。バイト一致だけで別メンバーの関数を置換すると閉包と登録の契約が変わる。                                    |
| 同一ページでの Teachable Machine の再利用 | 埋め込み版と小さいロード専用版を1つのメンバーに含む。実行時には既存の同版ランタイムの有無で片方を使う。                                                                   | 2つの登録実装を共有するには上流から共通の登録エントリーが必要。現状の分岐を残すことで、再読み込み時に TensorFlow の登録を繰り返さず、初回はオフラインで使える。                                                     |
| ZIP エントリー化                          | Standard SB3 の拡張は `extensionURLs` の data URL で読み込む。モデルだけを任意の ZIP エントリーへ移すと、VM の通常の読み込み・再保存ではその実体にアクセスできない。      | Plus 専用のローダーや Packager のファイル提供契約を使う経路は、標準 TurboWarp の互換性と分けて検討する。拡張の格納形式は [Issue #1114](https://github.com/kubohiroya/turbowarp-kamishibai-app/issues/1114) の範囲。 |

ランタイムメンバー内では同じ SVG の data URL が4群繰り返されていた。重複分は計2,096バイトで、削除しても16 MiBの余裕に対する効果は小さい。

## 有効化、検証、切り戻し

`scripts/sb3/dsl4-release-policy.ts` の `dsl4ReleaseCompactWasm` を生成時に読む。凍結済み rc.84 は従来の設定で再生成し、次の候補版から SIMD 2本の構成を選ぶ。現行の版番号での計測・テストは `createDsl4ReleaseSourceFiles({compactWasm: true})` を指定する。切り戻す場合は、新しい候補版を OFF で生成する。

回帰テストでは圧縮版の実SB3を生成し、15 MiB未満と1 MiB超の削減幅を確認する。SIMD の WASM 2本を復元して npm 配布物と照合し、通常版のバイナリが含まれないことを確認する。Scratch VM でプロジェクトを読み込む。Chromium では外部への通信を遮断して実ポーズモデルで Compute バックエンドを切り替え、SIMD 非対応を再現して CPU への切り替えも確認する。
